## 官方依据（本轮直接读取）

1. [Key Changes](https://modelcontextprotocol.io/specification/2026-07-28/changelog)：取消初始化握手，移除 `ping`、会话、GET SSE 和 DELETE 会话管理；增加逐请求元数据、发现和显式结果类型。
2. [Versioning and Compatibility](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)：每个请求选择版本，不再以初始化协商；不支持的版本返回 `-32022` 和 `data.supported/requested`。
3. [Basic Overview](https://modelcontextprotocol.io/specification/2026-07-28/basic/index)：必需 `_meta`、无请求 ID 时省略 id、`resultType` 和服务端身份。
4. [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)：必需版本/方法/名称头、头部绑定错误 `-32020`、未知方法 HTTP 404；简单同步服务可仅返回 JSON。
5. [Discovery](https://modelcontextprotocol.io/specification/2026-07-28/server/discover)：服务端必须实现 `server/discover`，客户端可不先发现而直接调用。
6. [Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)：结构化工具内容、注解、协议错误与工具执行错误、安全限流要求。
7. [Caching](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching)：缓存时长和可见性不得代替授权。
8. [Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) 与 [Client Registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)：继续 OAuth 资源绑定和逐次验证；DCR 已弃用但尚未移除，CIMD 并非本轮必须新增的服务能力。
9. [官方类型定义](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/schema/2026-07-28/schema.ts)：核对请求元数据、错误码、请求 ID 和结果字段。

这些依据只定义所实现子集，不代表本项目实现全部可选能力或已通过外部客户端认证。

## 实现决定

### 单一现代协议，不做双栈（历史决定，已由 2026-10-22 补充决定取代）

`src/lib/mcp/http-server.ts` 仅支持 `2026-07-28`：

- 保留 `server/discover`、`tools/list`、`tools/call`。
- 公共头部和逐请求元数据有效时，旧 `initialize`、`ping` 与其他未知 RPC 返回 HTTP 404 / `-32601`，不受版本支持情况影响。先检查必需头；缺头的旧 initialize 请求返回 HTTP 400 / `-32020`，不绕过校验。
- 不接受无 id 的客户端通知和 batch；缺失有效 id 的错误省略 id，不再返回 null。
- 每次请求独立验证；可以先 `tools/list` 或 `tools/call`，不缓存上次客户端声明，不依赖连接、session 或发现顺序。
- 正常结果统一带 `resultType: complete` 和 `_meta['io.modelcontextprotocol/serverInfo']`。同步工具的业务失败仍为 `isError: true` 的已完成结果，保留 409、输入验证等原业务代码。

不增加 SDK、Agent 框架、会话存储或假装可用的异步任务。仅声明 `tools: {}`，不声明 subscriptions、elicitation、sampling 或 SSE；GET、DELETE、HEAD、OPTIONS 对有效身份继续 405 / `Allow: POST`。

### 逐请求元数据与 HTTP 绑定

每个 POST 的 `params._meta` 必须含：

```json
{
  "io.modelcontextprotocol/protocolVersion": "2026-07-28",
  "io.modelcontextprotocol/clientCapabilities": {}
}
```

`clientInfo` 可选，若提供需含 name/version；它及 clientCapabilities 均是未验证的客户端声明，不作为 OAuth 授权依据，也不记录完整客户端上下文。

头部约束：

| HTTP 头 | 比较目标 |
| --- | --- |
| `MCP-Protocol-Version` | `_meta['io.modelcontextprotocol/protocolVersion']` |
| `Mcp-Method` | JSON-RPC `method` |
| `Mcp-Name`（仅 `tools/call`） | 原样安全 ASCII 或 `=?base64?{标准 Base64}?=` 中 UTF-8 字符串解码后与 `params.name` 一致 |

所有头部校验和 OAuth scope 检查在执行工具之前完成。ASCII 中的百分号、斜杠等按字面值比较，不做 URI 解码；非 ASCII、控制字符、首尾空白或原值匹配 sentinel 标记时必须用 Base64。标记大小写精确；拒绝非法/非规范标准 Base64 和非法 UTF-8，保留 BOM 防止改变比较结果；只解码一层。

| 情况 | HTTP / JSON-RPC |
| --- | --- |
| 公共头部及元数据有效的未知方法（不依赖版本支持情况） | 404 / -32601 |
| 缺少或类型错误的必需 `_meta` | 400 / -32602 |
| 必需头缺少、非法或与 JSON 不一致 | 400 / -32020 |
| 头和 JSON 一致但版本不支持 | 400 / -32022，data 含 supported/requested |
| 无效令牌、已撤销客户端或资源不匹配 | 401 / OAuth discovery challenge |
| 缺少操作所需 scope | 403 / 最小 step-up scopes challenge |
| 工具业务冲突或工具输入验证失败 | 200 / complete + isError，原业务代码保留 |
| 工具调用限流 | 429 / 应用错误码 429，附 Retry-After |
| 工具执行前限流计数存储故障 | 500 / -32603，不返回 result，也不执行工具 |

复合非法输入按处理顺序返回其中一个适用错误，不保证同时枚举全部错误。认证仍先于请求体读取；未认证请求不能探测受保护的工具或消耗工具额度。

### 限流与发现缓存

新增 `src/lib/mcp/rate-limit.ts`：

- 按已认证访问令牌的服务端 actorLabel 计数，每个自然分钟最多 120 次已知工具调用；不采用不可信的 clientInfo/name/IP 作为身份键。
- MongoDB `mcp_tool_rate_limits` 集合通过唯一 `_id = actorLabel:window` 和原子 `$inc` 保证多 worker 共享额度。`expiresAt` TTL 只清理旧计数，新窗口独立，不等待 TTL。
- 已通过协议、工具名及 scope 检查的工具尝试计数，包括后续工具参数/业务失败；发现请求、无效身份、缺 scope 和协议错误不计入工具额度。
- 超限请求不执行工具，可按 Retry-After 等待；不要因错误而盲目重放已产生不确定结果的写操作。计数存储故障时不放行工具，单独返回 HTTP 500 / JSON-RPC `-32603`；不把基础设施故障伪装成已完成的工具业务结果。
- `server/discover` 与 `tools/list` 明确 `ttlMs: 0, cacheScope: private`，HTTP 继续 no-store；角色过滤在每次请求按实际 scopes 执行。

### 工具与 OAuth 保持的边界

- 六个工具及 image.upload / guide.update / guide.publish 的组合权限不变。
- 静态工具输入 JSON Schema 仅在模块加载时生成；不缓存按用户过滤的工具列表。
- `upload_image` 的 openWorldHint 改为 true，因为它访问外部图片/存储；文案明确 URL 图片上限 10 MiB，但 Base64 必须装入 2 MiB 整体 JSON，原始图片小于约 1.5 MiB。不扩大请求体上限。
- 未引入 CIMD URL 请求，DCR/PKCE/同意/撤销、100 × 365 天有限令牌寿命及现有客户端注册继续保留。资源仍为原 `/mcp`，不轮换令牌，也不自动扩权。
- `/api/mcp-probe` 保持 SPEC 3.4 的旧协议固定数据诊断契约，不改成第二个正式业务入口，不以其成功证明 2026 客户端兼容。

## 2026-10-22 补充决定：双协议支持与向后兼容

- **当时状态**：源码已实现，测试 PASS；当时未正式发布部署，真实 Gemini 客户端双端验收待重新验证。当前运行事实见下节，不由此历史状态推定。
- **背景与现场证据**：2026-10-22 上午，用户使用真实 Google Gemini 官方移动端再次尝试添加 `/mcp`。Nginx 日志与 MongoDB 记录证明 OAuth 发现、DCR 动态注册、管理员同意与换码均已成功并签发有效 Token，但 Gemini 紧随其后的首次 POST `/mcp` 请求因不带 `MCP-Protocol-Version` 和 `Mcp-Method` 头，被单栈 2026 服务端直接返回 HTTP 400（错误码 `-32020`），导致添加失败。
- **决定**：放弃单栈 2026-07-28 策略，改为向后兼容双协议分流架构。
- **分流机制**：
  - 显式声明 2026 特征的请求（携带 `Mcp-Method` 头、调用 `server/discover` 方法、版本头不属于标准列表、或 `params._meta` 包含 `io.modelcontextprotocol/protocolVersion`）严格按 2026-07-28 规范处理；
  - 其余标准 MCP 客户端（如 Google Gemini Apps）进入标准兼容分支，支持标准的 `initialize` 握手、`ping`、`notifications/*` 通知确认（HTTP 202），以及无 2026 头部的 `tools/list` 与 `tools/call`。
- **安全与一致性**：两个分支在分流前统一执行 OAuth Bearer 鉴权、跨来源 Origin 校验、Accept 与请求体校验；`tools/call` 共用 `executeToolCall` 统一逻辑，严格执行 Scopes 校验、MongoDB 原子固定窗口限流（120 次/分钟）与 Revision 冲突保护。标准模式下 JSON-RPC 协议错误码返回 HTTP 200，以兼容标准 MCP SDK；非 200 HTTP 状态码的完整例外清单见 SPEC 3.3.3。
