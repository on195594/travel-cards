## 1. 决策摘要

继续采用 Next.js App Router + React + TypeScript + Zod + Mongoose 的全栈单体，以 Guide 为唯一核心聚合。保留 R2 图片存储和独立的 Gemini 候选生成模块；不改成 Meemo 的技术栈，不建设通用 CMS，不另建 Card 集合。[T1][T2]

优先级主线：**T0 独立验证与保存止损 → T1 轻量模块边界 / T2 发布与缓存一致性 → T3 编辑与内容维护 → T4 有证据才扩展**。安全修复不必等待拆目录；T1/T2 可在隔离门禁可用后分别推进。真实 R2/生产授权未完成只阻塞对应生产验收，不阻塞本地代码工作。

“独立验证”不等于另建生产 MongoDB。当前 SPEC 明确要求复用 Meemo 的 MongoDB 服务、网络与数据卷，也明确允许持有效 Token 的 Hermes 自动化创建、发布、修改与删除攻略。这两项决定予以保留，不擅自改成第二套数据库或强制所有内容人工发布。[T1]

## 3. 目标架构及复杂度预算

建议保留以下代码路径：

```text
src/app/                         页面、认证入口、Route Handlers
src/lib/guides/schema.ts         纯 Zod、输入/输出结构、Guide/GuideSummary 类型
src/lib/guides/repository.ts     Mongoose 模型、索引、数据库读写与序列化
src/lib/guides/service.ts        创建、编辑、发布、撤回、删除及业务约束
src/lib/ai/                     候选生成与来源处理，不持有管理写权限
src/lib/storage/                受限 R2 上传
src/components/guide-editor/    按实际职责渐进提取的编辑组件和 Hook
```

公共 Schema 和类型不导入 Mongoose、凭据或供应商 SDK；持久化、认证与供应商模块保持服务端专用。Next.js 缓存再验证留在框架边界，由小型统一函数调用，不塞入领域规则。业务错误可以有普通 code，再由 HTTP 层映射；不引入复杂异常层级。

依然是一个 Web 应用、一个既有共享 MongoDB 实例、两个逻辑数据库（meemo 与 travel_cards）以及已有外部 R2/Gemini。数据模型、数据库账号与生命周期责任应明确；两个应用不互读彼此的集合。

不新增 Repository 基类、DI 容器、独立 API 服务、消息代理、领域事件总线、多模型路由或持久任务系统。

### 4.1 配置来源、构建与健康检查

运行时变量建议继续采用 `.env.example` 后加载本地私有 `env_file` 的方案，删除遮蔽 `MONGODB_URI` 的硬编码 `environment` 项；本地文件保持 raw 处理，避免 `$` 出现在密码哈希/凭据中时被意外解释。若改用别的方案，必须迁移并验证，不能让两个来源竞争。[T4][T11][T12]

Compose 的端口和网络名插值来自 shell/Compose 项目环境，不是容器 `env_file`。文档必须分别说明输入位置；验证自定义端口、反向代理公共 origin、`AUTH_URL` 和数据库 URI 的实际组合。保留默认 `meemo_backend` 与当前生产绑定，参数化不意味着允许擅自重建共享网络或卷。

集成运行采用构建产物的生产启动路径。live 仅证明进程可服务；ready 在有限超时内探测数据库，并验证必要初始化失败会明确暴露。数据库断开→恢复必须能重新 ready；不能永久缓存一个失败/成功 Promise 的结论。ready 不调用 Gemini/R2、不执行建库或迁移、不回显连接串。

### 4.2 编辑安全必须先于组件整理

T0-07 至少引入发送快照/草稿代次和同步的 in-flight guard。React 状态中的 `busy` 不能单独作为双击、快捷键和异步链的互斥保证。

保存时捕获当前完整草稿与 saved revision；成功后只确认已发送快照。用户在请求期间输入的新内容必须保留为未保存。保存、发布、撤回、删除及上传采用明确的串行/互斥规则；不另建全局状态框架。

发布涉及“先保存、再发布”两个操作，不能把它们宣称为一个数据库事务。首批最简单策略是发布链执行期间锁定表单及候选采纳入口，保持链级 guard，保证公开的就是用户本次确认的快照；保存成功而发布失败要分别显示“保存已成功”和“本次发布失败/待确认”；只有读回状态确为 draft 时才能显示“尚未发布”，避免误判另一个 Token 客户端已完成的发布。不要用中间 `save()` 的 finally 提前解除整条链的保护。

409、超时、JSON/网络错误均保留草稿。对已知 Guide ID 的结果未知操作只读核对；首次创建没有可靠 ID 时禁止自动重发 POST，不用标题/正文相似就断言是本次成功写入。不为暂未实现的幂等键承诺 exactly-once。候选和上传结果绑定发起时的编辑会话；切换攻略后迟到回包不能写到另一篇攻略。

### 4.3 数据与图片恢复范围

备份前阻止新的浏览器和 Token 写请求，停止应用写者并排空上传/保存；同时确认是否有外部 R2 写者。仅停止浏览器编辑器或设置一个应用标志不足以证明静止。MongoDB 保留共享实例运行，只隔离本项目写入；实例级维护按第 11 节处理。

备份必须包含 `travel_cards` 数据、索引元数据、精确镜像、必要配置身份及已引用图片的实际字节、大小和独立校验值。不要把对象清单或上传 API fake 测试当作图片备份。R2 操作限定批准的专用 bucket/prefix；不扫描或更改历史 smoke 使用的共用备份 bucket。

隔离恢复默认使用合成攻略和 fake/本地测试对象，证明控制流程；真实备份抽样、R2 字节读回/恢复或新远端资源需另行授权，状态独立记录。恢复到隔离测试存储时，明确 public base URL 映射并检查实际图像可读，禁止通过原生产图片地址“假装恢复成功”。

恢复只允许批准的 `travel_cards` 命名空间，参数按 [T13] 及实际工具版本验证；校验 slug 唯一索引、`slugLocked`（含已撤回条目）、revision、日期和权限。另一数据库哨兵不得变化。密钥值、原始 Compose/inspect 环境列表不得进入验收日志。恢复旧备份之后重新核对公开状态、会话/Token 和未完成的外部调用，不能自动重放恢复前的发布队列。

**代码退出门槛：** 隔离 verify、保存安全反例、合成恢复通过；T1 可在所依赖门禁可用后开展。

**生产退出门槛：** 真实资源与备份范围核对、授权及回退可用；fake 成功不计作 R2 生产恢复验收。生产证明未授权不得标为完成，也不阻塞不依赖它的本地重构。

## 5. T1：只拆职责，不重构产品

**目标：让 Guide 可以长期演进，但不增加新的架构层级。**

| 编号 | 任务 | 验收标准 |
| --- | --- | --- |
| T1-01 | 从 guides.ts 提取纯 Schema、持久化和服务规则。 | HTTP 路径、JSON 错误、权限、revision CAS、slug 唯一/锁定、发布完整性规则保持一致；抽取前后使用同一组回归测试。 |
| T1-02A | 先建立内部 GuideSummary 与完整 Guide 的区别。 | 内部摘要不含正文，不通过空数组伪装详情；详情必须实查完整文档；HTTP 响应暂保留现有兼容形态。 |
| T1-02B | 单独迁移公开/管理列表的响应契约。 | 明确列表字段白名单、状态码和 consumer 清单，先修订 SPEC；旧响应字段删除或分页元数据改变都不得混入“纯重构”。已知调用者同步迁移后清理兼容映射。 |
| T1-03 | 统一浏览器请求/错误处理的小型入口。 | 保存、撤回、删除、上传、AI 失败能被一致展示；不再由每个组件临时解释相同错误。 |
| T1-04 | 建立服务端模块边界检查。 | 浏览器不能导入数据库/供应商/认证实现；用真实 production build 及负向导入用例验证，不只搜索 bundle 中有没有明文密钥。Vitest 对服务端标记的适配仅限测试环境。 |

`GuideSummary` 是读取投影，不是新集合或 CQRS 服务。保留 revision 为唯一并发权威，不启用第二套 `__v`。repository 的写方法必须要求 expectedRevision（新建除外），不能只由 service 先检查再无条件写。

**兼容策略：** T1-01/T1-02A 可保留一个仅位于 HTTP 边界、明确标为 legacy 的响应映射器，输出旧客户端预期形态；它不能作为完整 Guide 传入编辑器或 service。T1-02B 是单独的接口变更，内部不伪造详情与外部短期兼容并不矛盾。没有调用者清单就不删除旧字段；有实际外部兼容需要才评估版本入口，不默认创建 `/v2`。

结构抽取先冻结现有 HTTP/领域回归；输入 Zod 与持久化 Schema 保持各自职责，避免生成一套复杂 Schema 同步框架。发布规则、slug 锁、缺失/清空字段语义有实库测试。过渡 re-export 和响应映射器各自记录调用者及删除条件，不永久保留两套业务入口。

**退出门槛：** T1-01/02A 的重构无行为漂移；T1-02B 按明确批准的新契约及 consumer 验收，不能同时声称“响应没变”。Token 自动化仍可执行已授权能力。

## 6. T2：发布契约、自动化身份和缓存一致性

**目标：一次成功的管理动作对应可理解、可验证的公开结果。**

### 6.1 固定两条写入边界

| 调用来源 | 保留的能力 | 必须补齐的约束 |
| --- | --- | --- |
| 内置 Gemini 助手 | 候选、调整建议、问答。 | 不持有发布/删除/任意写入工具；采纳只进入本地编辑草稿，持久化仍走普通保存。 |
| 浏览器管理员 | 已有管理能力。 | Session、同源限制、服务端校验、expectedRevision。 |
| Hermes Token 客户端 | SPEC 已授权的创建、直接发布、更新、撤回、删除、上传与 AI 调用。 | 有效 Token 校验、相同业务规则和 revision 保护、请求来源追踪；不得因为 Token 路径而跳过内容规则。 |

近期不强行收窄现有 Token 权限。先由服务端生成 `authKind/actorLabel`，在结构化日志中记录请求 ID、动作、Guide ID、前后版本和结果；不记录 Token、正文和完整模型输入。如果以后确实需要草稿专用 Token，再修改 SPEC 并设计可审查的权限配置与迁移。

归因日志只用于定位问题，不等同于不可篡改审计账本。客户端任意传入的 actorLabel 不能当作认证来源；AuthKind 由服务端实际验凭结果产生。

“带来源的 AI 内容”不等于真实可靠；结构验证和来源关联都不能取代事实复核。[T7] 权限回归还要覆盖：无效 Bearer 加有效 Cookie 不能意外回退放行；有效 Bearer 与 Cookie 请求的 CSRF 路径分别验证；未授权请求在 JSON/multipart 读取和付费调用前拒绝；保留当前请求大小、文件签名及搜索长度限制。

### 6.2 明确已发布内容的保存语义

维持当前单版本 Guide：保存已发布攻略会直接更新公开内容，界面应明确提示“保存并更新公开内容”。不要以为已经存在独立的待发布修订稿。[T2]

继续使用 revision 保护更新、发布、撤回和删除。保持 SPEC 当前的 slug 稳定与撤回行为，不趁重构修改 publishedAt 的含义。只有出现真实的“在线版本不动、同时编写新版草稿”需求时，才评估单 Guide 内的受控发布快照；这不属于近期必做。

### 6.3 先降低缓存复杂度，再做优化

建议在此阶段：管理/草稿响应明确 `private, no-store`；公开正文、列表/检索响应及 sitemap 采用明确的动态读/`no-store` 策略，静态资源与公开图片独立缓存。认证/Token 存在或 `scope=admin` 的请求在代理上也不得共享缓存。必须检查生产代理，不能只改源站 header。

受控入口清单包括首页、`?q=` 直达搜索、公开列表 API、slug 详情、metadata、sitemap、客户端导航/RSC 响应及代理缓存规则。`generateMetadata` 与页面正文须使用同一次请求内的一致读取结果；允许请求内去重，但不引入跨请求的陈旧内容缓存。构建不能把数据库攻略烘焙成未声明的公开快照。

已有 revalidatePath 应收敛为可复用的框架侧处理，不把其视为外部 CDN purge 的替代。Next.js 官方说明 Route Handler 中的 revalidatePath 标记路径并在后续访问再验证，其作用域应按实际版本理解和测试。[T3][T10]

上线新缓存规则时，先显式清除或等待既有共享缓存失效，随后才能声明新契约成立；仅修改 Cache-Control 不会证明旧缓存已清除。

**推荐验收契约：** 在受控缓存完成迁移之后，撤回成功响应之后发起的新匿名请求，不能再通过列表、搜索、详情、metadata 或 sitemap 获得该攻略。并发中已经开始的请求、浏览器已打开的旧内容、用户下载和第三方搜索缓存不属于“可立即收回”的承诺。

撤回攻略不会自动销毁曾公开的 R2 图片。图片私密化需要另外的存储与访问设计，不在当前公开封面模型中暗示保证。

**写入与副作用分离：** DB 已提交后，日志、再验证或客户端刷新失败不等于 DB 已回滚。服务端不能因此再次执行 create/publish。错误/成功响应须能表达已知的写入结果；客户端收到无法判定的失败转为“结果待确认”并只读核对。对本阶段 no-store 架构，非关键刷新失败可记录警告；若关键公开可见性无法满足则不要声称撤回契约已通过，先阻断相关发布并修复入口。

**回退同样保护缓存：** 不直接回退到重新启用共享缓存的旧镜像/代理配置；回退包需保留已验证 no-store 规则，并完成受控旧缓存处理。不能因为回退就让已撤回内容重新可见。已打开页面/浏览器历史仍可能显示旧副本，应提示刷新；本方案不承诺远程擦除已分发内容。

| 编号 | 任务 | 验收 |
| --- | --- | --- |
| T2-01 | 固定 Session、Token、AI 权限矩阵并增加回归。 | 未授权请求全部失败；Token 仍能执行已授权的直接发布；AI 只能返回候选。 |
| T2-02 | 统一发布与保存语义，补来源日志。 | UI 与 API 对“保存已发布攻略”含义一致；能区分浏览器/自动化操作，不泄露凭据。 |
| T2-03 | 统一缓存策略和受控入口验证。 | 新建直接发布、修改、撤回、删除都覆盖；管理员和访客响应不会混用缓存；生产代理配置另行授权调整。 |

**退出门槛：** 状态转换、并发冲突与公开可见性测试一起通过，不能只验证数据库 status 字段。HTTP、HTML/metadata 和导航响应按锁文件中的 Next.js 版本验证；仅检查一个状态码或看按钮隐藏，不足以证明草稿/撤回内容未泄露。

## 7. T3：编辑器与内容维护的最小闭环

**目标：让经常编辑、发布和查找攻略的过程不丢稿、不误导、不隐藏内容。**

| 编号 | 任务 | 验收 |
| --- | --- | --- |
| T3-01 | 提取编辑器状态 Hook、AI 面板与封面上传组件。 | 一次只提取一个职责，不加入全局状态库；saved、draft、candidate 三种状态不混同。 |
| T3-02 | 改善冲突对照和恢复体验。 | 复用 T0-07 已完成的基本保存安全；本阶段只增强对照、错误定位、导航保护，不把数据丢失修复延后到这里。 |
| T3-03 | 给列表、检索及 sitemap 补齐遍历契约。 | 分页类型、默认/上限、唯一键排序和结束条件写入 SPEC；第 101/201 篇也能到达。首页服务端 `q` 与客户端/API 查询一致；sitemap 使用独立有界批量遍历，不能继承第一页上限。 |
| T3-04 | 核对来源和时间显示；必要时新增明确的内容复核字段。 | 来源获取时间、编辑时间与人工复核时间含义不同；修改标题不等于重新核验全部内容。新 reviewedAt 等字段先修改 SPEC。 |
| T3-05 | 建立只读图片引用盘点。 | 统计攻略引用与候选孤儿；不自动删除；不碰共用备份 bucket。不因删除一篇攻略而删除可能复用的对象。 |

未来若授权孤儿删除，必须限定专用 bucket/prefix、设置上传保护期、复核所有引用，并解决扫描与删除之间的并发写入；先 dry-run，再显式确认执行。不得以一个未经保护的定时清理任务代替生命周期设计。

分页不承诺跨多次请求的数据库快照：固定数据集要求无遗漏/重复；并发发布、修改排序字段时允许列表变化，客户端去重并支持重新加载。第一页响应包与后续页的兼容设计和 T1-02B 一并核对，不能出现两个相互冲突的列表契约。

**退出门槛：** 已批准的编辑器、列表和内容维护子任务各自通过；时间与来源不会被展示成虚假的“已核验”。T0 保存安全无论是否实施 T3，都必须成立。

**测试隔离。** 默认测试运行器创建带随机 run 标识的临时实例、数据库及存储目录。清理前同时核对资源标签/实例身份、精确库名、当前 run 标识；仅以库名含 `_test`、host 为 localhost 或设置 NODE_ENV=test 均不充分。禁止连接生产共享实例执行默认测试。采用已有测试实例时须具有独立身份和独立授权，不能以“不同库名”为由借用生产实例。清理仅删除本次创建的资源，不用全局 prune；失败也保留脱敏诊断且不误删其他运行的测试资源。

**恢复隔离。** 在一次性实例或严格核验的目标库中恢复；namespace allowlist、必要的重命名映射和命令参数按实际数据库工具版本验证。另设一份模拟另一应用的哨兵数据，前后内容/索引不变才算通过。生产恢复审批同时说明恢复点之后的合法写入如何处理，不能用数据丢失来掩盖代码回退失败。

**证据与秘密。** 一个任务回执只需 SHA、实际命令、工具版本、用例结果、隔离资源标识、相关哈希、未执行项和回退判断。证据留在授权的私有工作目录；Git 只保留脱敏结论与模板。环境变量原文、数据库 URI 密码、Token、用户正文、私有附件和未净化 inspect/Compose 输出不得作为公开日志。示例环境文件只有非生产占位值。

**实施与授权。** 两项目代码可独立推进，不互相等待完整路线结束；仅共享实例变更需要真正协同。新增存储字段、权限/可见性和公开 API 行为要先修订本项目权威契约。共享数据库不意味着共用认证 Cookie、集合、业务模型或自动公开 Meemo 内容；不做自动双向同步。
